# 블랙홀 프로젝트 — 최적화를 위한 게임 설계 원칙

최신화: 2026-09-28 — 8절에 지금 코드(`feature/블랙홀성장도`)가 각 원칙을 어떻게 지키는지와 아직 없는 것을 적었다. 1~7절의 예시 숫자(60 FPS, Planet 70개 등)는 확정 합격선이 아니다.

## 0. 우리가 생각하는 최적화

우리의 최적화는 두 단계로 생각한다.

첫 번째는 **기획 단계에서 불필요한 복잡도가 발생하지 않도록 게임 규칙을 설계하는 것**이다.

두 번째는 **게임이 만족해야 하는 성능 한계를 먼저 정하고, 실제 측정을 통해 그 기준 안으로 비용을 낮추는 것**이다.

핵심 질문은 다음과 같다.

> **“이 시스템은 최악의 경우 어디까지 커질 수 있는가?”**

그리고 개발 단계에서는 다음을 묻는다.

> **“우리가 보장하기로 한 최악 상황에서 실제 비용은 얼마인가?”**

특정 최적화 기술을 먼저 선택하지 않는다.

먼저 게임 규칙으로 복잡도의 상한을 만들고, 그 뒤 실제 성능을 측정해 필요한 부분만 개선한다.

---

# 1. Spawn은 시간에 묶지 않고 사건에 묶는다

개체가 단순한 시간 경과 때문에 끝없이 증가하지 않는다.

```text
X  1초마다 Planet 생성
X  시간이 흐를수록 무제한 증가

O  Level Up 시 공급
O  특정 Asteroid 파괴 시 공급
O  Session 시작 시 공급
O  명시된 Gameplay Event에서만 공급
```

즉,

> **시간이 오래 흘렀다는 이유만으로 월드가 무거워져서는 안 된다.**

Spawn에는 항상 명확한 Trigger와 공급 규칙이 존재해야 한다.

### 확인할 것

- 누가 Spawn을 발생시키는가?
- 한 이벤트에서 최대 몇 개가 생성되는가?
- Spawn 자체가 다시 Spawn을 발생시킬 수 있는가?
- 게임 진행에 따라 개체 수가 어디까지 증가할 수 있는가?

---

# 2. 연쇄 효과는 반드시 끝나도록 만든다

강력한 효과가 있다고 해서 무제한 연쇄를 허용하지 않는다.

예:

```text
Level Up
→ Planet 생성 [SpawnOnDeath 가능]

Planet 사망
→ Secondary Planet 생성 [SpawnOnDeath 불가]

Secondary Planet 사망
→ 종료
```

핵심 규칙은 다음과 같다.

> **효과가 만들어낸 결과가 다시 동일 계열 효과의 원인이 되지 않도록 한다.**

예:

```text
SpawnOnDeath로 생성된 Planet
→ SpawnOnDeath 금지

Explosion으로 발생한 결과
→ 같은 Explosion을 다시 발생시키지 않음

Reflect Damage
→ 다시 Reflect되지 않음

Chain Lightning
→ 최대 연쇄 횟수가 존재
```

연쇄 시스템에는 반드시 **끝나는 이유**가 있어야 한다.

코드에서 사고를 막는 것이 아니라 먼저 게임 규칙에서 끝나도록 만든다.

---

# 3. 전투 중 계산하지 않아도 되는 것은 전투 밖에서 결정한다

우리 게임에는 의도적으로 **휴식 / 업그레이드 Phase**가 존재한다.

이 시간을 단순한 메뉴 화면이 아니라 **게임 상태를 정리하고 다음 전투를 준비하는 경계**로 활용한다.

```text
Battle
────────────────
현재 규칙으로 플레이

Battle End
────────────────
전투 결과 확정

Rest / Upgrade
────────────────
노드 선택
성장 선택
스킬 구성
다음 전투 준비

Next Battle
────────────────
새로운 구성으로 시작
```

전투 중에 계속 모든 가능성을 확인하는 대신,

> **변경할 수 있는 시간과 실행하는 시간을 분리한다.**

전투 중에는 이미 선택된 규칙을 실행하고, 큰 상태 변화는 휴식 Phase에서 처리한다.

이렇게 하면 플레이어에게는 명확한 게임 흐름이 생기고, 개발자에게는 명확한 상태 경계가 생긴다.

---

# 4. HQ를 월드의 Root 좌표 `(0,0)`로 사용한다

HQ는 단순히 여러 객체가 참조하는 대상이 아니다.

> **HQ 자체를 Gameplay 공간의 논리적 원점 `(0,0)`으로 정의한다.**

```text
HQ
→ (0, 0)

Planet A
→ (+8, +3)

Planet B
→ (-4, +10)
```

주요 공간 규칙도 이 원점을 기준으로 설명한다.

```text
Orbit
→ (0,0) 기준

Spawn
→ (0,0) 기준 Offset

Skill Range
→ (0,0) 기준 반경

Matter Absorb
→ 현재 위치에서 (0,0) 방향

Black Hole 영향 범위
→ 원점으로부터의 거리
```

이렇게 하면 각 시스템이 서로 다른 중심점을 만들지 않는다.

```text
Player 위치
Skill 중심
Orbit 중심
Spawn 중심
Absorb 중심
```

을 각각 관리하는 대신 하나의 공간 언어를 공유한다.

핵심 원칙:

> **기준점을 계속 찾지 않는다. 기준점 자체를 좌표계로 만든다.**

이 규칙은 계산뿐 아니라 게임 규칙 설명과 디버깅도 단순하게 만든다.

---

# 5. 성장감을 Entity 수 증가에만 의존하지 않는다

후반부가 강해졌다고 해서 객체 수가 계속 증가해서는 안 된다.

```text
Lv 1
20개의 작은 Asteroid

Lv 20
40개의 Asteroid

Lv 50
60개의 Planet

Lv 100
60개의 Giant Planet
```

어느 시점 이후에는 개체 수 증가보다 다른 방법으로 성장감을 표현한다.

```text
크기 증가
HP 증가
희귀도 변화
보상 증가
종류 변화
화면 점유율 증가
파괴 규모 증가
더 큰 천체 등장
```

예:

```text
Asteroid
→ Moon
→ Planet
→ Giant Planet
```

핵심은:

> **Scale, Don't Multiply.**

화면을 더 많이 채우기 위해 객체를 계속 늘리지 않는다.

같은 수의 객체라도 더 거대한 존재로 바꾸면 게임의 성장감은 계속 커질 수 있다.

---

# 6. Gameplay Lifetime과 Presentation Lifetime을 분리한다

Gameplay에서 죽은 객체는 더 이상 살아 있는 객체처럼 취급하지 않는다.

```text
Planet HP <= 0

→ Death 확정
→ Reward 확정
→ Gameplay에서 제거
```

그 뒤에 화면에서:

```text
파괴
흡수
Trail
숫자 표시
연출
```

이 계속되더라도 그것은 이미 **결과를 보여주는 단계**다.

핵심은:

> **연출이 끝나지 않았다는 이유로 Gameplay 객체가 계속 살아 있을 필요는 없다.**

즉,

```text
Gameplay Lifetime
≠
Visual Lifetime
```

이다.

이 규칙은 게임 상태를 명확하게 유지하면서도 연출의 자유를 보장한다.

---

# 7. 성능 한계를 먼저 정하고, 기준 시나리오에서 측정하며 낮춰간다

개발 단계에서는 특정 최적화 기술을 먼저 선택하지 않는다.

먼저 **이 게임이 어떤 상황까지 안정적으로 돌아가야 하는지**를 정한다.

예:

```text
Target Platform
────────────────
우리가 지원하기로 한 최소 사양

Target Frame Rate
────────────────
60 FPS

Frame Budget
────────────────
16.67 ms
```

하지만 단순히 `60 FPS`라고 쓰는 것만으로는 부족하다.

**어떤 상황에서 60 FPS를 보장해야 하는가**까지 정의해야 한다.

예:

```text
Reference Performance Scenario

Black Hole Level 30
Planet 70개 활성
Special Planet 15개
동시 사망 20개
Chain Effect 최대 4단계
흡수 연출 발생
```

이처럼 우리가 정상 플레이에서 허용하는 가장 무거운 상황을 **Reference Performance Scenario**로 고정한다.

그리고 이 상황을 개발자가 언제든 빠르게 재현할 수 있어야 한다.

예:

```text
[Performance Debug]

FPS
Frame Time
Active Entity Count
Spawn Count
Death Count
Current Level
Current Battle Phase

+ Gold
Force Level Up
Spawn 10 Planets
Spawn 50 Planets
Kill All
Trigger Max Chain
Skip To Next Battle
Force Game Over
```

이 디버깅 툴의 목적은 편의를 위한 치트가 아니다.

> **우리가 성능을 보장하기로 한 상황을 반복해서 재현하기 위한 도구다.**

그 상태에서 실제 값을 측정한다.

```text
Reference Scenario

Frame Time     24.0 ms
Target         16.67 ms
```

그 다음 가장 큰 병목부터 하나씩 줄인다.

```text
24.0 ms
↓
21.5 ms
↓
19.2 ms
↓
17.1 ms
↓
16.3 ms
```

중요한 것은 어떤 기술을 사용했는지가 아니다.

중요한 것은:

```text
측정
↓
가장 큰 비용 확인
↓
원인 분석
↓
하나 개선
↓
다시 측정
```

이라는 과정이다.

각 개선의 효과도 숫자로 남긴다.

| 변경 | Before | After | 개선 |
|---|---:|---:|---:|
| 기준 상태 | 24.0ms | - | - |
| 개선 A | 24.0ms | 21.5ms | -2.5ms |
| 개선 B | 21.5ms | 19.2ms | -2.3ms |
| 개선 C | 19.2ms | 16.3ms | -2.9ms |

이렇게 하면 팀 전체가 다음을 알 수 있다.

- 현재 성능 기준이 무엇인지
- 어디가 실제 병목이었는지
- 어떤 변경이 효과가 있었는지
- 목표 대비 얼마나 여유가 남았는지
- 새로운 기능이 기존 기준을 깨뜨렸는지

핵심 원칙:

> **최적화를 기술 목록으로 관리하지 않는다. 성능 Budget과 측정값으로 관리한다.**

그리고 새로운 기능을 추가할 때도 같은 Reference Scenario에서 다시 측정한다.

# 8. 지금 코드에 적용된 모습 (2026-09-28)

원칙마다 규칙이 무엇으로 상한을 만들고, 어디가 아직 비어 있는지 적는다. 규칙 세부는 [GAME_RULES_MVP](GAME_RULES_MVP.md), [BATTLE_COMPOSITION_PLAN](BATTLE_COMPOSITION_PLAN.md), [SKILL_TREE_PLAN](SKILL_TREE_PLAN.md)에 있다.

| 원칙 | 지금 지키는 방식 | 비어 있는 것 |
|---|---|---|
| §1 Spawn은 사건에 묶는다 | 공급 계기는 전투 시작과 블랙홀 판 Level업(성장 공급) 둘뿐이다. 한 계기가 요청하는 수는 유한하다. 시간 경과로 생기는 적은 없다. 판 전체의 동시 생존 상한(`maxAliveEnemies`, 200 [임시])에 닿은 요청은 버리고 다시 나오지 않는다. 공급 수 노드를 모두 산 시작 공급이 상한을 넘으면 게임이 시작하지 않는다(`UpgradeContentCheck`) | 파괴 뒤 같은 종류 생성(세 번째 계기)을 넣을 때 "그 생성이 다시 생성을 부르는가"를 정해야 한다. 상한 값은 측정 전 [임시]다 |
| §2 연쇄는 끝나게 만든다 | 사망 효과를 가진 적은 효과 피해를 받지 않는다 → 효과로 생긴 사망은 새 효과를 부르지 않고, 대기열은 한 번 훑으면 끝난다. 연쇄 번개는 최대 횟수가 있고 같은 적을 다시 맞히지 않는다. 폭발은 한 번이다. 처치 버프는 피해를 만들지 않고, 다시 받아도 곱으로 쌓이지 않는다(남은 시간·배율 중 큰 쪽) | 되먹임(공격 주기 감소 → 처치 증가 → 버프 다시 획득)의 상한과 유효 공격 간격의 하한이 없다. 공격 속도 노드가 늘어나면 정한다 |
| §3 전투 밖에서 결정한다 | 판 조립 때 한 번: 방장의 업그레이드 표, 스킬 수치, 적 판 구성, (종류, 색, 황금)별 수치 표, 성장도의 색 비율·기본 변환 비율·판 Level 표, Level업마다 시간. 전투 중에는 노드 구매·진행 치트가 거부되고, 진행 상태(Gold·성장도)는 결산에서만 바뀐다. 처치 버프가 켜지고 꺼질 때만 Breaker 주기가 바뀐다 | — |
| §4 HQ = (0,0) | 출현 띠·공전·흡수 도착점이 HQ 원점 기준이다(`BattleSpace`). 블랙홀 그림도 원점의 원이다. 공격 중심은 HQ가 아니라 조준점이다 | 흡수 연출이 없어서 도착점 규칙은 아직 쓰이지 않는다 |
| §5 Scale, Don't Multiply | 성장감은 종류 변환(소행성 → 행성 → 별), 성장도별 색, 질량 계수(HP·Gold)로 낸다. 공급 수 노드는 상한 안에서만 늘린다 | 후반 판의 실제 개체 수는 측정하지 않았다 |
| §6 Gameplay ≠ Presentation | 사망은 `RecordDeath` 순간 확정되고 Gold·EXP가 그때 들어간다. 적·스킬·사망 효과·블랙홀 표현은 Core의 순번 있는 기록을 읽어 그릴 뿐 결과를 다시 계산하지 않는다. 판 정리는 결산 화면으로 넘어가기 전에 네 표현이 모두 비었는지 확인한다 | 파괴·흡수·숫자 연출이 아직 없다. 연출이 길어질 때의 동시 수 상한은 연출을 만들 때 정한다 |
| §7 한계를 정하고 측정한다 | 개발용 콘솔로 일부 상황에 들어갈 수 있다: Gold 더하기, 모든 노드 사기, 블랙홀 EXP 더하기(판 Level·목표), 성장도 −1 / +1(이정표 앞 성장도로 가기), 종류별 생성·파괴 요청, 스킬 켜기·끄기, 일시정지. Core 규칙은 Unity 없이 계약 113개로 검증한다(`tests/CoreSmoke`) | **목표 기기·FPS, Reference Scenario, 측정 도구가 없다.** FPS·프레임 시간·살아 있는 적 수 표시, "N마리 생성"·"최대 연쇄 일으키기" 같은 재현 명령, 측정 기록 표를 만들어야 한다. 계약은 규칙 검증이지 성능 측정이 아니다 |

### 다음에 할 일

1. 목표 기기와 목표 FPS를 정한다.
2. Reference Scenario를 지금 콘텐츠로 적는다. 예: 블랙홀 성장도 30, 별 단계 노드를 모두 산 판, 동시 생존 상한까지 공급, 전기 소행성·초신성 동시 사망.
3. 개발용 콘솔에 그 상황으로 가는 명령과 FPS·프레임 시간·적 수 표시를 더한다.
4. 그 상황에서 Core 계산과 Unity 표현의 비용을 나눠 측정하고, 7절의 표 형식으로 기록한다.
5. 그 결과로 동시 생존 상한 200을 확정한다.

# 팀원이 모두 기억해야 할 핵심 8문장

1. **시간이 오래 흘렀다는 이유만으로 Entity가 무한히 증가하지 않는다.**
2. **효과가 만든 결과가 같은 효과를 무한히 다시 발생시키지 않는다.**
3. **전투 중 계산할 필요가 없는 것은 Rest Phase에서 결정한다.**
4. **HQ는 단순한 대상이 아니라 월드의 Root 좌표 `(0,0)`다.**
5. **성장감은 Entity 수보다 크기와 스케일의 성장으로 표현한다.**
6. **Gameplay가 끝난 객체는 연출 때문에 계속 살아 있지 않는다.**
7. **최적화 기술을 먼저 고르지 않는다. 우리가 보장해야 하는 성능 한계를 먼저 정한다.**
8. **기준 상황을 반복해서 측정하고 가장 큰 비용부터 하나씩 낮춘다.**

# 최종 원칙

기획에서는:

> **복잡도가 무한히 커질 수 없도록 게임 규칙에 상한을 만든다.**

개발에서는:

> **필요한 성능 한계와 기준 상황을 먼저 정의하고, 그 상황을 반복 측정하며 실제 비용을 하나씩 낮춘다.**

전체 흐름은 다음과 같다.

```text
게임 규칙으로 복잡도 제한
        ↓
성능 한계 정의
        ↓
Reference Scenario 고정
        ↓
디버깅 툴로 즉시 재현
        ↓
측정
        ↓
가장 큰 병목 개선
        ↓
다시 측정
```

> **좋은 기획은 계산량의 상한을 만든다.  
> 좋은 개발은 그 상한에서 필요한 성능을 숫자로 증명한다.**
