# Reference Implementation — 구현 경계와 실험 결과

## 목적과 적용 범위

첨부된 Reference Implementation 가이드에 따라 가장 작은 플레이 흐름으로 경계를 구현했다.
기준 프로젝트는 `blackhole-client/dev`, 초기 커밋 `7a59810`이다.
코드 성향은 앞서 확인한 `ked-presentation-runtime/dev`의 책임·수명 분리 방향을 따른다.

현재 흐름: Session 생성 → 대상 출현 → 궤도 이동 → 단일/범위 스킬 → 피해·당김 → 사망 → 흡수 → 보상·질량 증가 → 공격력 강화 → 시간 종료 또는 수동 종료 → 새 Session.

## 이번 실험에서 정한 가정

- 조작 캐릭터 없이 마우스 조준점에 스킬을 사용한다. 플레이어 이동은 포함하지 않는다.
- 대상 2종은 HP·회전 방향·속도·보상이 다르며 같은 궤도 규칙을 공유한다.
- 살아 있는 대상은 안쪽 궤도에 머물고, 사망하면 빠르게 중심으로 떨어진다.
- 사망 자체는 보상을 주지 않는다. 흡수 확정 시 질량과 재화를 한 번 받는다.
- 집중 공격은 가장 가까운 하나, 중력파는 조준점 주변 전부에 피해와 당김을 준다.
- 빈 조준은 쿨다운을 소비하지 않는다.
- 모든 성장과 강화는 한 판 수명이다. 영구 저장·SkillTree·인증·네트워크는 만들지 않았다.
- 한 판 60초, 화면 내 대상 최대 32개, 강화 최대 5단계다. 모두 검증용 수치다.

## 상태의 주인과 변경 경로

| 경계 | 소유 상태 | 공식 변경 경로 | 외부에 맡긴 것 |
|---|---|---|---|
| GameSession | 실행/정지/종료, 경과 시간, 확정 결과 | Advance, TryCast, TryUpgrade, TogglePause, Stop | 피해·보상·강화 계산 |
| Playfield | 판 안 시스템의 연결 | 내부 Advance / TryCast | 개별 계산과 상태 전이 |
| SpawnSchedule | 출현 타이머, 순번 | Playfield에서 Advance | 개체 행동 |
| TargetWorld | 대상 목록, ID 발급 | 내부 Spawn / RemoveAbsorbed | 대상 HP·위치 전이 |
| TargetState | 개별 HP·극좌표·생명주기 | 내부 Move / ApplyDamage / Pull / TryAbsorb | 보상, Unity Transform |
| SkillLoadout / SkillState | 스킬별 쿨다운 | 내부 TryCast / Advance | 개별 스킬 실행 규칙 |
| ISkillEffect 구현 | 불변 효과 수치 | Execute | Session·보상·저장 |
| CombatResolver | 보유 가변 상태 없음 | Hit | 대상의 실제 상태 전이 |
| AbsorptionSystem | 보유 가변 상태 없음 | 내부 Resolve | 질량·재화 변경 규칙 |
| GrowthState | 질량·재화·흡수 수·강화 단계 | 내부 ReceiveAbsorption / TryUpgrade | 화면 표시 |
| ReferenceGameController | 입력과 화면 메시지 | Unity 생명주기, 입력 → Session 요청 | 게임 판정 |
| ReferenceWorldView | Sprite/Texture와 뷰 목록 | Synchronize / ClearTargets / Dispose | 게임 상태 변경 |

`internal` 변경 메서드는 Core 어셈블리 안에서만 호출된다. Unity는 상태를 읽고 Session에 요청한다.
목록은 읽기 전용 뷰로 노출하고 정의는 생성 후 수정하지 않는다.
조립 시 SpawnSchedule·SkillLoadout·GrowthState·Playfield는 판마다 새로 만든다. 가변 객체를 두 판이 공유해서는 안 된다.

## 실행 순서와 보상 보장

입력의 스킬 요청은 즉시 쿨다운·조준 조건을 확인하고 피해/당김을 적용한다.
다음 진행에서 쿨다운 → 대상 이동 → 흡수/보상/제거 → 출현 순서로 처리한다.

흡수는 `Defeated → Absorbed` 전이에 성공한 경우에만 보상을 지급한다.
이미 흡수된 대상은 다시 전이할 수 없고 해당 진행 안에 목록에서 제거된다.
단일 스레드 동기 실행을 전제로 하며 분산 처리의 exactly-once 보장을 주장하지 않는다.

Session 종료 후 모든 공개 게임 요청은 거절되거나 진행하지 않는다. 결과는 한 번만 캡처한다.
호스트는 종료 상태를 계속 표시할 수 있다. 재시작 때 이전 뷰를 제거하고 새 Session을 조립한다.

## 실제 구현으로 택한 경계

### Orbit

극좌표와 생명주기는 같은 대상 상태가 소유한다. 현재 두 대상은 동일한 궤도 규칙의 수치 변형이므로 별도 Orbit 서비스나 인터페이스를 만들지 않았다.
직선 돌진·추적처럼 다른 이동 방식이 필요해지면 `TargetState.Move`의 규칙을 분리할 근거가 생긴다.
현재 구현은 블랙홀 중심이 원점인 2D 모델이며 Unity 물리를 사용하지 않는다.

### Skill / Effect / Combat

단일 공격과 범위 공격+당김이라는 두 실제 규칙이 있어 `ISkillEffect`를 두었다.
수치 변형은 `ReferenceGame`의 정의 추가로, 새로운 행동은 효과 구현과 조립으로 추가한다.
SkillLoadout·GameSession에는 스킬 종류별 분기가 없다. 테스트의 제3 효과도 같은 경로로 실행한다.

별도 EffectSystem·이벤트 버스·등록 프레임워크는 필요하지 않았다.
현재 CombatResolver는 유효 대상에 피해/당김을 전달하는 작은 경계다. 이후 방어·저항·시전자 귀속이 필요하면 이곳에서 규칙을 검토한다.

### Session

Session은 수명과 요청 허용 여부를 맡고 Playfield는 판 안 처리 순서를 맡는다.
현재 하나의 시간제 모드만 있어 GameMode 인터페이스를 만들지 않았다.
시간 종료 외 목표가 생기면 종료 판정 규칙을 분리한다.

### Upgrade / Reward

보상은 대상 정의에, 흡수 확정 순서는 AbsorptionSystem에, 재화·질량·강화 변경은 GrowthState에 둔다.
하나의 공격력 강화만 있어 별도 Upgrade 프레임워크는 만들지 않았다.
SkillTree 도입 시 획득 조건·그래프와 강화 효과를 분리하고 재화 변경 경로를 유지한다.

## 검증 범위

공유 계약 테스트 13개는 다음 위험을 확인한다.

- 사망과 흡수 보상 시점 분리, 중복 지급 방지
- 단일/범위 대상 선택과 당김
- 쿨다운·잘못된 스킬·빈 조준 결과
- 강화 실패 시 상태 보존, 성공 후 실제 피해 배율 적용, 최대 단계
- 일시정지와 종료 뒤 모든 게임 변경 차단
- 새 판 상태 분리, 잘못된 콘텐츠 거부, 제3 스킬 확장
- 출현 수 제한 및 대상 2종 사용
- 자동 조준을 사용한 최소 플레이 흐름에서 성장·강화·종료 도달

Unity 에디터가 없는 작업 환경에서 구현했으므로 화면/입력/에디터 컴파일은 직접 실행 확인하지 않았다.
GitHub `Core contracts` 결과는 순수 규칙 검증에 한정한다.

### Unity 수동 확인

1. SampleScene Play 후 중심 블랙홀과 대상 2종이 보이는지 확인한다.
2. 청록 대상 위에서 1을 눌러 사망 → 회색 낙하 → 흡수 뒤 재화 2 증가를 확인한다.
3. 밀집한 대상을 향해 2를 눌러 범위 피해와 당김을 확인한다.
4. 재화 6 이상에서 U를 눌러 차감·공격 배율 증가를 확인한다.
5. P를 눌러 이동·타이머·쿨다운이 멈추고 스킬·구매가 거절되는지 확인한다.
6. 종료 후 결과가 유지되는지, R로 질량·재화·쿨다운이 초기화되는지 확인한다.
7. EditMode 테스트를 실행한다.

## 팀 분배에 사용할 수 있는 작업 경계

| 작업 후보 | 함께 합의할 경계 | 독립 확인 방법 |
|---|---|---|
| 대상/Orbit | 위치·HP·생명주기와 생성 책임 | 이동·사망 전이 사례 |
| 스킬/전투 | 조준 입력, 유효 대상, 피해 요청과 결과 | 신규 효과 계약 테스트 |
| 블랙홀/성장 | 흡수 확정, 보상 수치, 강화 비용 | 중복·실패·성공 사례 |
| Session/진행 | 시간·목표, 종료·재시작 | 상태 전이 사례 |
| UI/표현 | 읽기 모델과 사용자 요청 | SampleScene 대체 화면 |
| 콘텐츠/통합 | 정의 검증·초기 조립·핵심 흐름 | 공유 계약 및 플레이 확인 |

이 표는 팀원 배정이나 일정 확정이 아니다. 실제 기획과 각 팀원의 역량을 반영해 시스템 목록·의존 지도·티켓으로 나눈다.

## 남은 결정과 한계

- 실제 플레이어/캐릭터, 적의 공격과 실패 조건은 팀 기획에서 정해야 한다.
- 성장의 영구성, 저장, 스킬트리 노드/간선·AND/OR 조건은 후속 범위다.
- 현재 샘플 뷰는 두 종류를 색으로 구분한다. 제품 콘텐츠가 늘면 표현 메타데이터로 옮긴다.
- 풀링과 대규모 대상 탐색 최적화는 하지 않았다. 현재 32개 범위를 넘어서는 성능은 측정하지 않았다.
- 가변 프레임을 작은 간격으로 나누지만 고정 틱/결정론/네트워크 동기화 엔진은 아니다.
- 미래 협동에서는 플레이어/시전자 식별과 상태 변경 권위, 접속 수명, 복제 모델을 추가해야 한다.
- 스킬 실행은 신뢰할 수 있는 동기 코드다. 사용자 작성 스크립트의 실패 복구나 효과 롤백은 없다.

이 구현은 제품 아키텍처의 최종형이 아니다. 핵심 흐름에서 확인한 경계를 팀 작업 분배의 출발점으로 사용한다.
