# M8 — 변화 실험과 정리

상태: 완료(2026-09-24) · 선행: M7 (보류된 확장은 미구현으로 명시)

## 목표

만든 경계가 실제 변화에 버티는지 작은 실험으로 확인하고, 결과를 팀이 쓸 수 있는 문서로 정리한다. v1에서 가장 쓸모 있었던 "변화가 어디까지 번지는가"를 v2 규칙 기준으로 다시 본다.

## 변화 실험

각 실험은 바뀐 파일과 바뀌지 않은 파일을 기록한다. 실험용 변경은 테스트 콘텐츠에만 두고, 게임 규칙으로 남기지 않는다.

| 실험 | 확인할 것 | 관련 경계 |
|---|---|---|
| 수치만 다른 Enemy 종류 추가 | 콘텐츠만 바뀌는가 | B4, B9 |
| Enemy Runtime Stat에 보정 하나 연결(예: 테스트용 HP 배율) | 기본 정의·Enemy 본체·출현이 바뀌지 않는가 | B4 |
| Skill 수치에 보정 하나 연결(예: 반경 증가) | 공격 범위와 화면 원이 함께 바뀌는가 | B5, B7 |
| Skill 기준점을 다른 것으로 교체(예: HQ 위치) | Skill 실행 구조가 바뀌지 않는가 | B5 |
| Player 2명으로 판 조립(테스트) | 전역 Player 가정이 어디에 남았는가. 보상 귀속 정책이 없다는 사실이 약속대로 드러나는가 | B1, B6 |
| AimPoint를 다른 출처로 채움(예: HQ 위치를 AimPoint로) | Skill·Player가 마우스를 모르는가 | B1, B5 |
| 흡수 연출을 끄거나 길이를 바꿈 | 보상과 게임 결과가 바뀌지 않는가 | B7 |

## 착수 조건 (2026-09-24 확인)

| 착수 전에 정할 것 | 결정 | 근거 |
|---|---|---|
| 이미 검증된 실험의 처리 | 다시 하지 않는다. 검증한 계약과 커밋으로 기록한다 | 아래 대조표. M4~M7이 같은 경계를 이미 계약으로 확인했다 |
| Core를 바꾸는 실험 | 작업 트리에서 임시로 바꾸고, 바뀐 파일과 계약 결과를 기록한 뒤 되돌린다. 커밋하지 않는다 | 비범위: 새 게임 규칙 추가, 실험 결과를 게임 콘텐츠에 남기기 |
| 테스트 콘텐츠만 쓰는 실험 | 계약으로 남긴다. 이번에 해당하는 두 실험은 기존 계약이 이미 확인하고 있어 새 계약을 만들지 않았다 | 이 문서: 실험용 변경은 테스트 콘텐츠에만 둔다 |
| 팀 분배 표의 소요 시간 | 시간을 적지 않는다. 바뀐 파일 수, 계약 수, 다른 시스템과의 접점으로 상대 규모(S/M/L)와 근거만 적는다 | 사용자 선택. 이 Reference의 구현 기록은 팀 속도를 대표하지 못한다 |
| 규모 측정 | 목표 없이 참고 수치만 잰다. 적 32·256·1024마리에서 Core의 프레임당 시간과 할당. 합격선은 만들지 않는다 | 사용자 선택. 목표 대상 수가 정해지지 않았다 |

### 실험 대조표

| 실험 | 상태 | 처리 |
|---|---|---|
| Enemy 실행 수치에 보정 연결 | M6에서 검증(HP 배율 노드) | 기록: `Upgrade.PurchasedEffectsChangeNextBattle`, `Enemy.RuntimeStatsLeaveBaseDefinitionUnchanged` |
| 구매 → 다음 전투의 변화, 기본 정의 불변 | M6에서 검증 | 기록: `Upgrade.*`, `*.RuntimeStatsLeaveBaseDefinitionUnchanged` |
| Player 2명 조립, 두 Player의 독립성 | 검증됨 | 기록: `World.PlayersAreAListNotASingleton`, `Skill.EachPlayerHasOwnSkills`, `Death.RewardedMultiplayerHasNoPolicy`, `Upgrade.PlayerStatesAreIndependent`, `Upgrade.SharedWorldPurchasesInMultiplayerHaveNoPolicy` |
| 생성 공급 구간 추가, HQ 성장 임계값 변경 | M5에서 콘텐츠만으로 검증 | 기록: `Growth.*` |
| 연출 생략·전투 정리가 보상을 바꾸지 않음 | 검증됨. Core 계약은 화면 없이 돈다 | 기록: `Death.*`, `Death.StopAndRestartDoNotGrantRewards` |
| 사망 효과 하나의 추가가 어디까지 번지는가 | M7 커밋이 기록 | M7 커밋의 바뀐 파일과 안 바뀐 파일을 정리 |
| Skill 수치 보정(반경)과 화면 원 | 계약은 검증. 화면은 코드로만 확인(M6 플레이 확인 생략) | 사용자 플레이 확인 |
| 수치만 다른 Enemy 종류 추가 | 검증됨. 테스트 데이터로만 종류를 더한다 | 기록: `Enemy.SupplyCreatesKindsInRequestOrder`, 그 밖에 종류를 더하는 계약 다수 |
| AimPoint를 다른 출처로 채움(HQ 위치) | 검증됨. HQ 위치 (0, 0)를 조준점으로 넣는다. Core에는 마우스 개념이 없다 | 기록: `Skill.HitsEveryEnemyInsideAndNoneOutside` |
| Skill 기준점을 HQ로 교체 | 새로. Core가 바뀐다 | 임시 변경 후 기록하고 되돌림 |
| 사망 효과 수치를 구매로 강화 | 새로. M7 발견의 확인. Core가 바뀐다 | 임시 변경 후 기록하고 되돌림 |
| 흡수 연출 끄기·길이 변경 | 새로. 표현만 바뀐다 | 코드 확인과 사용자 플레이 확인 |

## 정리할 문서

- **v2 예제집**: v1 SYSTEM_CATALOG처럼 시스템 후보별로 목적, 핵심 흐름, 만들며 부딪힌 질문([구조]/[임의]), 기획이 정할 규칙, 접점, 변화 실험 결과를 적는다.
- **GAME_RULES 갱신**: 만들며 생긴 새 질문과, 사용자가 답한 것을 반영한다.
- **[임시] 값 목록**: 최종 상태로 정리한다. 무엇이 여전히 미정인지 한눈에 보이게 한다.
- **규모 측정**: 목표 대상 수가 정해졌으면 그 수로 Core 비용을 잰다(Unity 측정은 별도).

## 결과

완료: 2026-09-24

**한 일**

- 실험 대조: 위 대조표의 실험 12개 중 8개는 기존 계약과 커밋으로 확인했다. 새로 한 실험은 아래 4개다.
- E3 Skill 기준점을 HQ로(임시 변경, 되돌림)
  - 바뀐 곳: 기준점 종류(`SkillOrigin`), Skill(HQ 참조), 전투 조립(HQ를 Skill보다 먼저 만듦), 로더의 종류 이름. 계약 1개를 더해 64개 통과, 분리 빌드 경고 0.
  - 바뀌지 않은 곳: 화면(범위 원은 Skill에 기준점을 묻는다), 적, 사망, 구매, 성장, 세션.
- E4 사망 효과 수치를 구매로 강화(임시 변경, 되돌림)
  - 바뀐 곳: 구매 효과 종류와 대상 검사(`UpgradeEffect`), 적용 자리(`UpgradeModifiers`), 적(출현 때 확정한 효과), 출현, World(효과를 적에게서 읽음). 계약 1개를 더해 64개 통과, 분리 빌드 경고 0.
  - 바뀌지 않은 곳: 로더(효과 종류를 열거형 이름으로 읽는다), 효과 처리(`DeathEffects`), 구매 흐름, 세션 조립, 화면.
- E5 흡수 연출 길이: 코드로 확인했다. Core는 Unity를 모른다. 길이 0은 아래 발견을 보라.
- E6 반경 보정과 화면 원: 코드로는 범위 원이 Skill의 실행 반경을 읽는다. 사용자 플레이 확인은 아래 검증에 적는다.
- 규모 측정: `tests/CoreBench`를 추가했다. 결과는 [v2 예제집](SYSTEM_CATALOG.md) 부록에 있다.
- 문서
  - [v2 예제집](SYSTEM_CATALOG.md): [임시] 최종 목록, 상태의 수명, 한 단계의 순서, 변화의 전파 범위, 시스템 후보 12개, 계약 목록, 규모 측정.
  - [팀 분배 자료](TEAM_SPLIT.md): 목적·소유 상태·입출력, 선행 작업·독립 검증·인수 기준, 공동 수정 지점, 상대 규모.
  - GAME_RULES 11·16절: 새 질문(효과 강화와 생성 시 확정의 관계, 번개의 대상 선택 세부, 여러 효과의 적용 순서).

**검증**

- 실험을 되돌린 뒤 CoreSmoke 63개 통과, 분리 빌드 경고 0·오류 0.
- 사용자 Unity 플레이 확인: 하지 않았다. 사용자가 확인 없이 커밋을 지시했다. E6(반경 보정과 화면 원)과 E5(길이 0)는 코드 확인으로 남는다.

**발견**

- 대조한 실험의 대부분이 이미 계약으로 확인돼 있었다. M4~M7이 경계를 계약으로 확인하는 방식으로 진행됐기 때문이다.
- E3: Skill이 기준점을 스스로 찾는 구조라, 새 기준(HQ)을 쓰면 Skill의 의존이 늘고 조립 순서가 바뀐다. 화면은 기준점을 Skill에 물어서 바뀌지 않았다.
- E4: M7은 효과를 적 종류 정의에서 바로 읽는다. 그래서 전투마다 다른 효과 수치를 줄 수 없다. 적의 실행 수치처럼 출현 때 확정한 효과를 적이 가져야 했다. 생성 시 확정 규칙이 효과 수치에도 적용되는지는 GAME_RULES 11절의 새 질문으로 올렸다.
- E5: 연출 길이를 0으로 하면 진행률이 첫 프레임에 0/0이 되어 위치가 NaN이 될 수 있다(`WorldView`의 흡수·번개·피격 연출, 코드 확인만 함). 연출을 끄는 설정은 길이와 따로 두어야 한다.
- 규모: 번개 한 번의 비용이 적 1024마리에서 유지 프레임 하나보다 크다. 튈 때마다 전체 목록을 훑고, 죽은 적을 목록에서 지울 때 뒤를 당긴다.
- 공동 수정 지점: `World.cs`, `ContentData.cs`, `ContentLoader.cs`, `SampleContent.cs`가 마일스톤 커밋 7개 모두에서 바뀌었다.

**재점검 항목의 답**

- v2가 PLAN 1절의 목적(경계의 체감)을 달성했는가? 대부분 달성했다. 시스템 후보 12개의 흐름, 상태의 주인, 접점을 실제로 만들고 계약 63개로 확인했다. 변화의 전파 범위도 실험으로 기록했다. 다만 다인 보상, 저장, 공간은 정책이 없다는 사실만 드러냈다. Unity 호스트는 자동 검증이 없다.
- 다음에 기획이 먼저 정해야 할 것(여러 후보의 인수 기준을 바꾸는 순서):
  1. HQ 유지 범위와 공간(HQ 크기·출현 거리·시야). 성장, 출현, 조립, 화면이 바뀐다.
  2. 다인 보상과 구매의 합성. 조립 검사, 보상 지급, 구매 적용의 세 곳이 함께 바뀐다.
  3. 적 공급 수량과 최대 적 수. 규모 측정의 목표가 된다.
  4. 노드 목록과 가격. 노드 저작 툴의 형식과 함께 정한다.
  5. 영구 저장의 범위.
- 다음 단계: Reference를 더 넓히기보다 팀 설계로 넘어가는 것을 권한다. 남은 확장은 대부분 기획 미정에 막혀 있고, 구조 질문은 실험으로 답이 나왔다. 결정은 사용자가 한다.

**계획과 달라진 점**

- 계약을 새로 만들 예정이던 두 실험(수치만 다른 적 종류, 조준점의 다른 출처)은 기존 계약이 이미 확인하고 있어 만들지 않았다.
- 규모 측정 도구를 `tests/CoreBench`로 남겼다. v1은 측정 코드를 남기지 않았다.

## 최신 규칙 추가 실험과 팀 분배 산출물

- 생성 공급 구간 추가: 적 본체/행동을 고치지 않고 구성 변경.
- HQ 성장 임계값 변경: 구매 해금과 독립적인지 확인.
- 구매 → 다음 전투의 스킬/적/공급/보상 변화와 기본 정의 불변.
- 두 Player의 조준점·스킬·구매 상태 독립성은 보상 거부 테스트와 별개로 검증.
- 사망 효과 하나의 변화가 구매·세션·표현에 어디까지 전파되는지 기록.
- 연출 생략과 공간 정리가 처치 보상을 바꾸지 않는지 확인.
- 후보 시스템별 목적·소유 상태·입출력·선행 작업·독립 검증 방법·인수 기준·공동 수정 지점을 표로 정리한다.
- 예상 소요 시간은 구현 기록과 팀 경험을 근거로 범위를 제시한다. 담당자와 확정 일정은 임의로 배정하지 않는다.
- 목표 수량이 없으면 성능 목표를 만들지 않는다. 측정 환경과 Core/Unity의 범위를 구분한다.
- Reference를 계속 확장하기보다 이 자료로 팀 설계와 티켓 분배에 넘어갈 수 있는지 확인한다.
