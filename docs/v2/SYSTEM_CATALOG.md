# System Catalog — Reference v2 예제집

갱신: 2026-09-24 · 기준: dev M0~M7(`16641ae`)과 M8 변화 실험

이 레포는 팀 게임의 설계 초안이 아니다. 블랙홀 키우기 게임의 시스템을 한 번씩 실제로 만들어 보면서, 각 시스템의 목적·규칙·흐름·책임을 체감하려고 만든 실물 예제집이다. v1 예제집은 [docs/v1](../v1/SYSTEM_CATALOG.md)에 있다.

가져갈 것은 코드나 클래스 구성이 아니라 다음 질문이다.

- 이 시스템은 왜 존재하는가?
- 어떤 상태와 규칙을 다루는가?
- 어떤 순서로 동작하는가?
- 다른 시스템과 어디에서 만나는가?
- 기획이 바뀌면 어느 부분이 달라지는가?

아래 시스템 후보는 "우리 게임의 시스템 목록"이 아니다. Reference에서 한 번 나눠 본 책임 덩어리다. 실제 기획에 따라 합쳐지거나, 나뉘거나, 사라질 수 있다.

**실제 게임 규칙은 [GAME_RULES.md](../GAME_RULES.md)에 있다.** 이 예제집에서 [임의]로 표시한 것은 규칙이 아니다. 팀 분배용 표는 [TEAM_SPLIT.md](TEAM_SPLIT.md)에 있다.

## 2. v2에서 얻은 관점

**상태의 주인과 수명.** 값마다 누가 갖는지와 언제 사라지는지를 정했다.

| 수명 | 상태 |
|---|---|
| 콘텐츠(바뀌지 않음) | 종류 정의, 노드 정의, 성장 노드, 판 시간 정의 |
| 진행(전투를 넘어 유지) | PlayerState: Gold, 산 노드 ID, 전투 잠금 |
| 전투(판마다 새로) | World, Player(조준점·Skill), HQ(EXP·Level), 적, 판 시간, 공급 대기 |
| 한 Advance | 사망 기록, 사망 효과 적중 기록 |

실행 값은 정해진 때 한 번 계산한다. Skill 수치는 전투 조립 때, 적 수치와 보상은 출현 때, 성장 공급량은 공급 요청 때다. 공유 정의는 어느 쪽에서도 바뀌지 않는다.

**한 단계의 순서.** 대부분의 결정이 한 단계 안의 순서였다.

```text
이동 → Skill(피해 → 사망 확정 → Gold·HQ EXP·Level → 사망 기록 → 효과 대기)
     → 사망 효과 → 성장 진행(공급 요청·시간 연장) → 공급된 적 생성
     → (단계 뒤) 종료 판정
```

순서를 바꾸면 결과가 달라지는 자리마다 계약이 있다.

| 순서 | 바뀌면 | 계약 |
|---|---|---|
| 성장 진행이 종료 판정보다 먼저 | 마지막 단계의 처치가 시간을 늘리지 못한다 | `Growth.ExtensionCountsBeforeTimeEnds` |
| 공급은 단계 끝 | 새 적이 같은 단계의 Skill에 맞는다 | `Growth.SuppliedEnemiesJoinFromNextStep` |
| 사망 효과가 성장보다 먼저 | 효과 처치의 EXP가 그 단계의 시간 연장에 들어가지 못한다 | `DeathEffect.EffectKillsCountBeforeGrowthAndTimeEnd` |
| 긴 프레임을 1/30초 단계로 나눔 | 한 번의 긴 단계 안에서 공급이 틱 뒤로 밀려 연쇄 성장이 멈춘다 | `Growth.LongFrameMatchesShortFrames` |

**변화가 어디까지 번지는가.** 실제로 바꿔 보고 바뀐 파일을 확인했다. 티켓을 자를 때의 근거다.

| 변화 | 바뀐 곳 | 바뀌지 않은 곳 | 근거 |
|---|---|---|---|
| 수치만 다른 적 종류 | 콘텐츠 데이터 | 코드 전부 | `Enemy.SupplyCreatesKindsInRequestOrder` |
| 성장 구간·임계값 변경 | 콘텐츠 데이터 | 코드 전부 | `Growth.*` |
| 기존 효과 종류로 업그레이드 노드 추가 | 콘텐츠 데이터 | 코드 전부 | M6 |
| 조준점을 다른 출처(HQ 위치)로 채움 | 없음 | Player, Skill | `Skill.HitsEveryEnemyInsideAndNoneOutside` |
| Player 2명 | 없음. 보상이나 공유 구매가 있으면 조립이 거부된다 | Player 목록, 조준점, Skill | `World.PlayersAreAListNotASingleton`, `Death.RewardedMultiplayerHasNoPolicy` |
| 첫 사망 효과 추가(M7) | Combat 새 파일 3개, 적 종류 정의, World(대기열·기록), 콘텐츠 데이터·로더, 샘플, 화면(번개 선) | 적 본체, Skill, 공급·출현, 성장, 세션, 구매, HUD, 전환 | M7 커밋 |
| Skill 기준점을 HQ로(M8 실험 E3) | 기준점 종류, Skill(HQ 참조 추가), 전투 조립(HQ를 Skill보다 먼저 만듦), 로더의 종류 이름 | 화면(범위 원이 기준점을 읽음), 적, 사망, 구매, 성장 | M8 결과 |
| 사망 효과 수치를 구매로 강화(M8 실험 E4) | 구매 효과 종류·대상 검사, 효과 적용 자리, 적(출현 때 확정한 효과), 출현, World | 로더, 효과 처리, 구매 흐름, 세션 조립, 화면 | M8 결과 |
| 흡수 연출 길이 | 표현 샘플 값 하나 | Core 전부 | 구조(Core는 Unity를 모른다). 길이 0은 문제가 있다(4절 표현과 호스트) |

**화면이 읽는 기록.** 규칙은 사망 기록과 효과 적중 기록을 남기고, 화면은 순번으로 한 번씩 소비한다. 한 프레임에 여러 단계가 진행돼도 기록을 놓치지 않는다. 화면은 결과를 결정하지 않는다.

## 3. 시스템 후보 요약

| 후보 | 목적 | Reference에서 확인한 흐름 | 기획이 정할 규칙 | 합쳐지거나 나뉠 가능성 |
|---|---|---|---|---|
| 전투 세션 | 한 판을 시작하고 끝낸다 | 진행(시간 분할) → 단계 → 종료 판정 → 결과 1회 | 끝나는 조건, 멀티 종료 | 종료 조건이 늘면 판정이 따로 나뉨 |
| 진행 상태와 전투 조립 | 전투를 넘는 상태를 지키고 새 전투를 만든다 | 진행 → 조립(보정 계산) → 전투 → 종료 → 구매 → 다음 전투 | 유지 범위, 영구 저장, 다인 | 저장이 생기면 저장 시스템이 붙음 |
| 콘텐츠 정의·검증 | 데이터를 안전하게 공급한다 | 저작 데이터 → 경로 진단 → 공유 정의 | 저작 도구, 형식 | 각 시스템에 흩어질 수 있음 |
| HQ 성장 | 블랙홀의 성장 진행도 | EXP 누적 → Level | EXP 공식, 구간 | 성장 진행과 합쳐질 수 있음 |
| 성장 진행과 공급 | 성장이 판을 바꾼다 | 새 Level → 공급 요청·시간 연장 → 단계 끝 생성 | 트리거, 수량, 종류 | 웨이브가 생기면 공급 규칙이 커짐 |
| 출현 | 요청받은 적을 만든다 | 위치 → 실행 수치·보상 확정 → 행동 | 위치 규칙, 난수 | 공급과 합쳐질 수 있음 |
| 적과 행동 | 적의 상태와 움직임 | 이동 → 피해 → 사망 확정 | 종류, 행동, 크기 | 행동이 늘면 행동이 따로 나뉨 |
| Passive Skill | 플레이어 자동 공격 | 주기 → 기준점 → 원 안 대상 → 피해 요청 | 스킬 목록, 수치, 판정 | 두 번째 스킬부터 종류가 나뉨 |
| 피해·사망·보상 | 처치를 한 번 확정한다 | 피해 → 사망 → Gold·EXP·기록·제거 | 다인 분배 | 사망 효과와 합쳐질 수 있음 |
| 사망 효과 | 적의 죽음이 부르는 게임 효과 | 대기 → 대상 선택 → 피해(같은 사망 절차) → 적중 기록 | 효과 목록, 강화 | 효과가 늘면 효과마다 나뉨 |
| 업그레이드 | 성장 방향을 고르게 한다 | 구매 판정 → Gold 차감 → 다음 전투의 적용 자리 | 노드, 가격, 선행 | 저작 툴(별도)과 짝 |
| 표현과 호스트 | 규칙을 화면과 입력에 연결한다 | 입력 → 요청 → 진행 → 기록 읽기 → 화면 | UX, UI, 아트, 연출 | UI / 월드 화면 / 입력으로 나뉨 |

## 4. 시스템 후보별 정리

질문의 답에 붙은 표시는 다음과 같다.

- **[구조]**: 구조상 이유가 있는 선택이다. 팀에서 다시 검토할 가치가 있다.
- **[임의]**: 샘플을 돌리려고 정한 규칙이다. 버려도 된다.
- **[규칙]**: GAME_RULES에서 확정한 규칙을 따른 것이다.

### 전투 세션

- **목적**: 한 판의 수명을 관리하고, 판이 끝난 뒤의 변경을 막는다.
- **플레이어 관점**: 남은 시간, 성장할 때 늘어나는 시간, 일시정지, 종료.
- **핵심 흐름**: 프레임 진행 → 1/30초 이하 단계로 나눔 → 단계마다 "제한 시간을 넘지 않게 자르기 → World 단계 → 종료 판정" → 끝나면 결과 1회 → 이후 진행 거절.
- **Reference가 던진 질문**
  - 경과 시간은 누가 갖는가? → 진행을 실행하는 쪽(SessionRunner)이 갖고, 종료 규칙(TimeLimitRule)은 판정만 한다. [구조]
  - 시간 연장은 공유 정의를 바꾸는가? → 아니다. 판마다의 제한 시간(Limit)이 늘어난다. 진행 제한, 종료 판정, 남은 시간 표시가 같은 값을 본다. [구조]
  - 연장이 그 단계의 종료 판정에 들어가려면? → 성장 진행이 단계 안에서 시간을 늘려야 한다. 조립 때 판 시간의 참조를 성장 진행에 넘긴다. [구조]
  - 일시정지하면 무엇이 멈추는가? → 진행 전체가 멈춘다. 조준점은 입력 상태라 계속 받는다. [구조]
  - 기록(사망, 효과 적중)은 언제 비우는가? → 다음 진행이 실제로 일어날 때. 일시정지 중에는 남는다. [구조]
  - 재시작은 초기화인가? → 새 조립이다. [구조]
- **기획이 정할 규칙**: 끝나는 조건(시간·목표·실패), 멀티 종료, 종료와 공격 틱이 겹칠 때의 순서.
- **다른 시스템과의 접점**: 진행·일시정지·종료 요청이 모두 여기를 지난다. 종료하면 PlayerState의 전투 잠금을 푼다.
- **바뀌면**: 새 종료 조건은 진행 전 자르기와 진행 후 판정의 두 자리에 붙는다. 두 번째 조건이 없어서 교체 인터페이스는 만들지 않았다.
- **구현 참고**: `Core/Session/GameSession.cs`, `SessionRunner.cs`, `TimeLimit.cs`

### 진행 상태와 전투 조립

- **목적**: 전투를 넘어 남는 상태(Gold, 구매)를 지키고, 그 상태로 새 전투를 만든다.
- **플레이어 관점**: 전투가 끝나면 구매 화면, 다음 전투에서 구매 효과. 새 진행은 처음부터.
- **핵심 흐름**: 진행 상태 → 참가자 검사 → 구매 효과 모음 → 정책 검사 → Skill·출현·공급 조립 → HQ·World → 시작 배치 → 전투 잠금 → 전투 → 종료 때 잠금 해제.
- **Reference가 던진 질문**
  - 무엇이 전투를 넘어 남는가? → PlayerState(Gold, 산 노드 ID)만. HQ EXP·Level은 전투마다 초기화한다. [임의](레퍼런스 근거)
  - 구매를 무엇으로 기록하는가? → 노드 ID. 콘텐츠에 없는 노드를 산 진행으로 조립하면 오류다. [구조]
  - 전투 중 구매와, 한 진행이 두 전투에 들어가는 일을 어떻게 막는가? → 전투 잠금 하나로 막는다. [구조]
  - 조립이 실패하면? → 모든 검사를 통과한 뒤에만 잠근다. 실패한 조립은 진행을 묶지 않는다. [구조]
  - 새 진행과 다음 전투는 같은 입구인가? → 다르다. `Create`는 새 진행, `CreateBattle`은 기존 진행을 받는다. [구조]
  - 정책이 없는 다인 조합은? → 조립 때 거부한다. 처치 중에 일부 보상만 적용되는 상황을 만들지 않는다. [구조]
- **기획이 정할 규칙**: 유지 범위, 영구 저장, 다인 보상과 구매의 합성.
- **다른 시스템과의 접점**: 구매(PlayerState), 세션 종료(잠금 해제), 모든 실행 값 계산(조립 때 보정을 넘김).
- **바뀌면**: 지금 전투를 넘어 남는 상태는 PlayerState뿐이다. 구매가 노드 ID라 콘텐츠 객체를 참조하지 않는다. 무엇을 영구 저장할지는 미정이다(GAME_RULES 16절). 저장 형식은 만들지 않았다.
- **구현 참고**: `Core/Players/Player.cs`, `Core/Session/SessionAssembler.cs`

### 콘텐츠 정의·검증

- **목적**: 수치·종류 데이터를 검증해 공유 정의로 공급한다.
- **플레이어 관점**: 없음. 기획·툴 담당의 작업면이다.
- **핵심 흐름**: 저작 데이터 → 1단계(판 설정, HQ, 적, 출현, Skill) → 2단계(시작 배치, 성장 노드, 업그레이드 노드: 1단계 색인으로 참조 해석) → 노드 사이 규칙 → 공유 정의. 오류가 하나라도 있으면 정의를 내지 않는다.
- **Reference가 던진 질문**
  - 오류를 몇 개 보고하는가? → 전부, 경로(`Enemies[light].DeathEffect.Kind` 등)와 함께. 부분 통과는 없다. [구조]
  - 수치 규칙은 어디에 있는가? → 정의 생성자 한 곳. 로더는 그 생성자를 호출해 경로를 붙인다. 규칙을 두 번 쓰지 않는다. [구조]
  - 종류 이름은 어떻게 해석하는가? → 명시 목록이나 열거형 이름으로. 숫자 문자열을 통과시키지 않고, 가능한 값을 진단에 싣는다. [구조]
  - 선택 칸(사망 효과, 선행 노드)은? → 비어 있으면 없음. [임의]
- **기획이 정할 규칙**: 저작 방식(ScriptableObject, 외부 파일, 툴), 담당, 노드 저작 툴과의 형식.
- **다른 시스템과의 접점**: 모든 시스템의 정의가 여기를 지난다. 새 정의 종류마다 데이터 칸, 로더 해석, 생성자 규칙이 하나씩 늘어난다.
- **바뀌면**: 종류가 늘면 로더가 가장 자주 함께 바뀐다(M5·M6·M7 모두). 여러 사람이 동시에 고칠 가능성이 가장 높은 파일이다.
- **구현 참고**: `Core/Content/`

### HQ 성장

- **목적**: 블랙홀의 성장 진행도를 가진다.
- **플레이어 관점**: 블랙홀이 커지고 Level이 오른다.
- **핵심 흐름**: 사망 확정 → HQ EXP 누적 → 임계값을 넘은 만큼 Level 상승.
- **Reference가 던진 질문**
  - EXP는 언제 들어오는가? → 사망 확정 때. 흡수 연출이 끝날 때가 아니다. [규칙](레퍼런스와 일부러 다름)
  - 한 번에 여러 Level을 넘으면? → 한 번에 오른다. 효과는 성장 진행이 Level마다 한 번씩 실행한다. [구조]
  - HQ가 성장 효과까지 실행하는가? → 아니다. HQ는 EXP와 Level만 가진다. [규칙]
  - 커지면 공간도 바뀌는가? → 화면 크기만 바뀐다. 출현 거리는 그대로다. [임의](레퍼런스 근거)
- **기획이 정할 규칙**: EXP 공식, 특정 구간, 유지 범위, 크기와 공간의 관계.
- **다른 시스템과의 접점**: 사망(EXP 입력), 성장 진행(Level 읽기), 화면(크기).
- **구현 참고**: `Core/Hq/`

### 성장 진행과 공급

- **목적**: 성장이 판을 바꾸게 한다(적 추가, 시간 연장).
- **플레이어 관점**: 성장하면 소행성이 늘고 시간이 는다.
- **핵심 흐름**: 단계 안에서 새로 도달한 Level을 낮은 것부터 → 공급 요청·시간 연장 → 단계 끝에 공급된 적 생성.
- **Reference가 던진 질문**
  - 공급과 생성은 같은 일인가? → 다르다. 공급은 무엇을 얼마나, 생성은 어디에 어떻게다. 요청을 모아 단계 끝에 만든다. [구조]
  - 새 적은 언제부터 맞는가? → 다음 단계부터. [구조]
  - 성장 공급을 늘리는 구매는 시작 배치에도 적용되는가? → 아니다. 공급 출처(시작, 성장)를 구분해 성장 공급에만 더한다. [구조](레퍼런스: 성장 때 추가되는 수를 늘리는 노드)
  - 주기 생성은? → 없다. GAME_RULES는 주기 생성을 확정 규칙으로 두지 않았고, 레퍼런스에도 근거가 없다. [규칙](현재 설계 방향)
- **기획이 정할 규칙**: 공급 트리거, 수량, 종류 비율, 최대 적 수, 전체 흡수 구간.
- **다른 시스템과의 접점**: HQ(Level), 판 시간(연장), 출현(생성), 구매(공급량 보정).
- **구현 참고**: `Core/Progression/GrowthProgression.cs`, `Core/Supply/`

### 출현

- **목적**: 요청받은 적을 실제로 만든다.
- **플레이어 관점**: 적이 블랙홀 둘레에 나타난다.
- **핵심 흐름**: 위치(HQ 기준) → 실행 수치·보상·(행동) 확정 → World에 추가.
- **Reference가 던진 질문**
  - 실행 수치는 언제 정하는가? → 출현 때 한 번. 살아 있는 적에 구매를 다시 적용하지 않는다. [규칙]
  - 위치는? → HQ에서 일정 거리, n번째 적은 각도 n × 간격. [임의]
  - 행동 구현은 누가 고르는가? → 조립 때 넘긴 해석기. 테스트만 다른 해석기를 꽂는다. [구조]
  - 난수를 쓰면? → Reference에는 난수가 없어 계약이 결정적이다. 쓰려면 공급원을 드러내야 테스트할 수 있다. [구조](v1과 같은 질문)
- **기획이 정할 규칙**: 출현 위치 규칙, 겹침, HQ 크기와의 관계.
- **다른 시스템과의 접점**: 공급(요청), 구매(수치·보상 보정), 적(생성).
- **구현 참고**: `Core/Spawn/`

### 적과 행동

- **목적**: 적 개체의 상태와 움직임.
- **플레이어 관점**: 블랙홀 둘레를 도는 소행성.
- **핵심 흐름**: 이동(행동이 다음 위치 계산) → 피해 수용 → 최초 사망이면 true.
- **Reference가 던진 질문**
  - 위치의 원본은? → 적. 행동은 다음 위치만 계산한다. [규칙]
  - 행동은 교체할 수 있는가? → 적 본체는 행동 인터페이스만 안다. 테스트 대역으로 교체한다. [구조]
  - 사망은 누가 확정하는가? → 적 자신이 한 번. 이미 죽은 적은 피해를 받지 않는다. [규칙]
  - 공전은 어떻게? → HQ와의 거리를 유지하고 원을 따라 돈다. [임의]
- **기획이 정할 규칙**: 적 종류, 행동 종류, 크기의 게임 의미(피격 범위).
- **다른 시스템과의 접점**: 출현(생성), Skill·사망 효과(피해), 사망(확정), 화면(읽기).
- **구현 참고**: `Core/Enemies/`

### Passive Skill

- **목적**: 플레이어의 자동 공격.
- **플레이어 관점**: 마우스 주변 원이 주기마다 적을 친다.
- **핵심 흐름**: 주기 → 기준점 → 원 안의 살아 있는 적 목록 복사 → 적마다 피해 요청.
- **Reference가 던진 질문**
  - 기준점은 누가 주는가? → 정의의 기준점 종류가 정한다. 첫 Skill은 소유 Player의 조준점이다. 마우스는 호스트만 안다. [구조]
  - 대상 목록을 왜 복사하는가? → 피해 중에 죽은 적이 목록에서 빠지기 때문이다. [구조]
  - 긴 프레임에 틱을 몇 번 치는가? → 지난 주기만큼 모두. [구조]
  - 첫 틱과 빈 틱은? → 첫 틱은 0초. 조준점이나 대상이 없어도 타이머는 흐른다. [규칙](첫 틱 0초는 유지 사항)
  - 구매 보정은 모든 Skill에 붙는가? → 아니다. 대상 Skill을 지정한다. Skill은 각자 특성을 가진 개별 존재다. [구조](사용자 확인)
  - 판정은? → 적 중심이 원 안. 조준점이 없으면 빈 틱. [임의]
- **기획이 정할 규칙**: 새 스킬 목록, 수치, 겹침 판정, 조준점 부재.
- **다른 시스템과의 접점**: Player(조준점), 조립(실행 수치), 피해(World), 화면(범위 원·틱).
- **바뀌면**: 기준점 종류를 추가하면 Skill이 그 기준(예: HQ)을 알아야 한다. 그래서 조립 순서까지 바뀐다(M8 실험 E3).
- **구현 참고**: `Core/Skills/`

### 피해·사망·보상

- **목적**: 처치를 한 번 확정하고 보상을 반영한다.
- **플레이어 관점**: 적을 부수면 Gold와 블랙홀 EXP.
- **핵심 흐름**: 피해 요청(출처 기록) → 적의 사망 확정 → Gold(Player)·HQ EXP·사망 기록 → 목록 제거 → 사망 효과가 있으면 대기열.
- **Reference가 던진 질문**
  - 보상은 언제? → 사망 확정 때 한 번. 흡수 연출과 무관하다. [규칙]
  - 보상 값은? → 출현 때 확정한 실행 보상. [구조]
  - 피해 출처는 보상 수령자인가? → 아니다. 기록일 뿐이다. [규칙]
  - 단일 Player 보상 전제는 어디에 있는가? → 두 곳이다. 조립 검사와 지급. 다인 정책이 생기면 함께 바꾼다. [구조]
  - 전투 정리는 처치인가? → 아니다. 보상이 없다. [규칙]
- **기획이 정할 규칙**: 다인 Gold 분배와 HQ EXP 반영.
- **다른 시스템과의 접점**: 적(확정), Player(Gold), HQ(EXP), 사망 효과(대기열), 화면(기록).
- **구현 참고**: `Core/World/World.cs`(DealDamage), `Core/Combat/Damage.cs`, `DeathRecord.cs`, `Core/Enemies/EnemyReward.cs`

### 사망 효과

- **목적**: 특정 적의 죽음이 부르는 게임 효과(첫 효과: 전기 연쇄 번개).
- **플레이어 관점**: 노란 적을 부수면 번개가 근처 적으로 튄다.
- **핵심 흐름**: 사망 확정 → 대기열 → Skill 단계 뒤에 순서대로 처리 → 대상 선택 → 피해(같은 사망 절차) → 적중 기록.
- **Reference가 던진 질문**
  - 효과는 누구의 것인가? → 적 종류 정의가 지정하고, 처리는 적 본체 밖의 전투 처리가 한다. [규칙]
  - 효과가 효과를 부르면? → 효과는 효과를 가진 적을 치지 않는다. 연쇄는 없다. [규칙](레퍼런스와 같다)
  - 그래도 대기열이 필요한가? → 규칙대로 재귀 없이 대기열로 처리한다. 효과로 죽은 적의 효과는 같은 대기열 뒤에 붙는다. [규칙]
  - 대상 선택, 출처, 성장과의 순서는? → 1절의 [임의].
  - 효과 수치를 구매로 강화하려면? → 효과를 적 종류 정의에서 바로 읽으면 전투마다 다른 값을 줄 수 없다. 출현 때 확정한 효과를 적이 가져야 한다(M8 실험 E4). 생성 시 확정 규칙이 효과 수치에도 적용되는지는 새 질문이다. [구조]
- **기획이 정할 규칙**: 두 번째 이후 효과, 효과 강화 노드, 갈라짐 확률, 등급 배율.
- **다른 시스템과의 접점**: 사망(입력과 출력이 같은 절차), 적(대상), 화면(적중 기록).
- **구현 참고**: `Core/Combat/DeathEffects.cs`, `DeathEffectDefinition.cs`, `DeathEffectHit.cs`

### 업그레이드

- **목적**: 전투 밖에서 성장 방향을 고르게 한다.
- **플레이어 관점**: 구매 화면에서 노드를 사면 다음 전투가 달라진다.
- **핵심 흐름**: 구매 판정(전투 중, 이미 삼, 선행, Gold) → Gold 차감·노드 ID 기록 → 다음 전투 조립 때 효과 모음 → 효과 종류별 적용 자리.
- **Reference가 던진 질문**
  - 노드에 무엇이 있는가? → ID, 가격, 선행 노드, 효과 목록. 위치·구역은 툴과 화면의 정보다. [구조]
  - 실패한 구매는? → 상태를 전혀 바꾸지 않는다. [구조]
  - 효과는 어디에 붙는가? → 종류마다 한 자리. Skill 수치(조립 때), 적 HP·보상(출현 때), 성장 공급량(공급 요청 때). [구조]
  - 여러 효과가 같은 수치에 붙으면? → 콘텐츠의 노드 순서로 쌓는다. 지금 샘플에서는 더하기와 곱하기가 섞이지 않아 차이가 드러나지 않는다. [임의]
  - 선행이 여럿이면? → 하나만 받는다. AND·OR 정책이 없다. [임의]
- **기획이 정할 규칙**: 노드 목록, 가격, 강화 횟수, 선행 정책, 구역 잠금.
- **다른 시스템과의 접점**: PlayerState(Gold·기록), 조립(효과 모음), 각 적용 자리(Skill, 출현, 공급), 콘텐츠(노드 형식), 노드 저작 툴(별도).
- **바뀌면**: 기존 종류로 노드를 더하면 데이터만 바뀐다. 새 종류는 종류 이름, 대상 규칙, 적용 자리를 하나씩 더한다. 적용 대상이 적의 새 특성이면 적의 실행 상태까지 번진다(E4).
- **구현 참고**: `Core/Upgrades/`

### 표현과 호스트

- **목적**: 규칙을 화면·입력·전환에 연결한다.
- **플레이어 관점**: 모든 화면, 마우스, 구매 화면, R·P 키.
- **핵심 흐름**: 입력 → 조준점·요청 → 진행 → World 읽기 → 화면 맞추기. 전투가 끝나면 화면 정리 → 구매 화면 → 다음 전투 조립.
- **Reference가 던진 질문**
  - 화면이 게임 상태를 바꾸는가? → 아니다. 매 프레임 World를 읽기만 한다. [구조]
  - 한 프레임에 여러 단계가 진행되면? → 기록을 순번으로 한 번씩 소비한다. [구조]
  - 범위 원의 크기는? → Skill의 실행 반경. 화면이 따로 정하지 않는다. [규칙]
  - 연출 시간은? → 실제 시간. 일시정지 중에도 흐른다. [임의]
  - 연출을 끄려고 길이를 0으로 하면? → 진행률이 첫 프레임에 0/0이 되어 위치가 NaN이 될 수 있다(코드 확인, 실행 안 함). 끄기는 길이 0이 아니라 따로 두어야 한다. [구조]
  - 전투 전환은 누가? → SessionLauncher. 진행의 수명도 여기서 가진다. [구조]
- **기획이 정할 규칙**: UX, UI, 아트, 연출, 공간 배치 트리 화면(툴과 별도), 일시정지 연출.
- **다른 시스템과의 접점**: 세션(요청), 진행 상태(구매 화면), 모든 기록.
- **구현 참고**: `Unity/`

## 5. 아직 다루지 않은 것

- 캐릭터의 게임플레이, HQ HP·패배, 네트워크.
- 영구 저장, 다인 보상·구매 정책.
- 두 번째 스킬, 두 번째 사망 효과, 효과 강화 노드(실험만 했다).
- 전체 흡수 구간, 크기의 게임 효과(피격 범위), 난수.
- 공간 배치 트리 화면과 노드 저작 툴(별도 작업), 밸런스.
- Unity PlayMode 테스트. Unity 호스트는 마일스톤마다 사람이 플레이해서 확인했다.

### 규모 측정 (Core만, 참고 수치)

목표나 합격선이 아니다. `tests/CoreBench`로 다시 잴 수 있다.

- 환경: AMD Ryzen 5 9600X, Windows 11(10.0.26200), .NET 8.0.21, Release, 계층 컴파일 끔.
- 유지: 적이 HQ 둘레를 돌고 죽지 않는다. Skill 하나가 0.5초마다 둘레 한 곳을 친다. 1/60초 진행 6000번의 평균.
- 사망과 번개: 첫 프레임에 전기 적 한 마리가 죽어 번개가 3번 튀는 판과, 전기 적이 없는 판의 첫 프레임 시간 차이(400판의 중앙값).

| 적 수 | 유지 (μs/프레임) | 유지 할당 (B/프레임) | 전기 적 1마리 사망과 번개 (μs) |
|---|---|---|---|
| 32 | 0.8 | 0 | 1.2 |
| 256 | 6.2 | 0 | 8.5 |
| 1024 | 25.9 | 0 | 32.7 |

- 유지 비용은 적 수에 비례한다(이동의 삼각함수, Skill의 대상 탐색). 할당은 없다.
- 번개 한 번이 1024마리에서 유지 프레임 하나보다 비싸다. 튈 때마다 전체 목록을 훑고(최대 적중 수 × 적 수), 사망한 적을 목록에서 지울 때 뒤를 당긴다. 한 프레임에 여러 전기 적이 죽으면 그 수만큼 곱해진다.
- Unity 위의 Core 비용, 화면(적마다 GameObject), IMGUI HUD 비용은 포함하지 않았다.
